# Concept: GitHub Actions & Scheduled Workflows

The Fleet pipeline is designed to run autonomously. While you can run the scripts locally via `bun run`, the primary intended deployment is via GitHub Actions.

## The Workflows

The skill injects two primary workflow templates into the `.github/workflows/` directory.

### 1. `fleet-dispatch.yml` (The Planner)

This workflow is responsible for Phases 1 through 4. It runs the Analyze, Plan, Validate, and Dispatch scripts.

**Triggers:**
* `schedule`: A cron job. By default, it runs daily at 6am UTC (`cron: "0 6 * * *"`).
* `workflow_dispatch`: Allows a human to manually trigger the planning phase via the GitHub UI.

**Execution:**
It sets up the Bun runtime, installs dependencies from `scripts/fleet/package.json`, and executes `bun fleet-plan.ts` (which internally executes the dispatch). It requires the `JULES_API_KEY` secret to authenticate the Staff Engineer planning agent.

### 2. `fleet-merge.yml` (The Resolver)

This workflow is responsible for Phase 5. It handles the sequential, CI-gated merging of the PRs generated by the Dispatch workflow.

**Triggers:**
* `workflow_dispatch`: By default, this is manual. It is highly recommended that a human reviews the generated PRs before clicking "Run workflow" to merge them sequentially.

**Execution:**
It uses the `GITHUB_TOKEN` to query the GitHub API for open PRs authored by Jules. It iterates through them, updates their branches (`gh pr update-branch`), waits for CI (`gh pr checks`), and squashes them (`gh pr merge`). It also requires `JULES_API_KEY` to handle the Re-dispatch loop if merge conflicts occur.

## Concurrency Control

Both workflows use GitHub Actions `concurrency` groups:

```yaml
concurrency:
  group: fleet-dispatch
  cancel-in-progress: false
```

This ensures that only one instance of the planner or merger is running at a time. If the planner runs while another planner is still evaluating, it queues up rather than causing race conditions or duplicate task generation.
